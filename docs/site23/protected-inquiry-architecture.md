## Goal and security boundary

BAGDigital needs **one small, first-party marketing inquiry**, independent from Core tenant credentials, Francisco's HCP connection, Google OAuth, customer authentication, agents, and payments. GitHub Pages can serve the visual form but cannot enforce a trusted submission policy. The selected light Field Notes design stays intact until a separately reviewed UI cutover.

Architecture, with topology/provider selections **proposed, not enrolled or deployed**:

    Visitor browser (untrusted)
       | HTTPS fetch, explicit form acknowledgment, anti-bot widget
       v
    Static bagdigital.tech (GitHub Pages: cannot securely validate itself)
       | POST application/json; explicit credential-free HTTPS request
       v
    NEW, ISOLATED marketing intake service (host/domain TBD, OFF by default)
       | 1. Kill switch, method/type/body cap and allowlisted Origin hint
       | 2. Server-owned schema/consent normalization, no extras
       | 3. ONE durable atomic admission: source/global quotas + concurrency + token-HMAC-only PENDING claim
       | 4. ONE bounded server-side Siteverify, exact host/action/expiry, terminal token state
       | 5. Separate durable canonical-content logical delivery claim after verified challenge
       | 6. One fixed sender/recipient, structured text-only email delivery
       v
    Approved outbound email relay (provider TBD) --> fixed BAGDigital inbox

    Separately: aggregate redacted status/abuse metrics, bounded alarms and rollback.
    NO direct form POST to FormSubmit; NO customer Core APIs or database access.

The email relay and limiter are independent adapters. The deployment must not load tenant/provider keys or a Core database credential. Use no customer account cookies. One controlled public endpoint only; staging/prod keys, email sandboxes, durable stores, alert routes, quotas and off-switches are separately isolated. No shared staging secrets or production receiver.

## Public contract (proposed, subject to independent review)

- HTTP POST only; reject other methods with 405 and a constant Allow: POST. Reject unsupported Content-Type with 415. Accept a JSON object only as strict UTF-8; read no more than **16 KiB of bytes** total including encodings and delimiters, from both Content-Length and the actually streamed body. Reject invalid UTF-8 with fatal decoding, duplicate JSON keys including decoded escape-equivalent keys, arrays/scalars, nested structures, proto-pollution keys, unknown keys, malformed Unicode including lone surrogate code units and invalid JSON. **Built-in JSON.parse alone is NOT sufficient:** Stage 1 must use a pinned, testable strict duplicate-aware JSON parser/tokenizer that rejects key repetitions before materializing the object; no regex-based duplicate detector or parse-then-check workaround. Reject with 400/413/415 and make zero external dependency calls.
- Exact allowlist: name (1–100 Unicode code points), email (bounded valid mailbox, maximum 254 ASCII characters), optional business (0–100 Unicode code points), service (one enumerated website/workflow-planning/integration-planning/support selection), message (20–2,000 Unicode code points), processing_ack **exactly** string "yes", challenge token (1–2,048 ASCII characters), request_id (strict UUIDv4 syntax, caller-supplied hint ONLY). Normalize trimmed name/business/message to Unicode NFC before code-point limits and canonical dedupe; enforce explicit UTF-8 byte caps as well as code-point caps after normalization; email lowercasing/domain normalization rules must be documented and testable before Stage 1. Reject non-strings (including null), invisible/control characters in header-bound values, CR/LF in email/name, duplicate keys, unknown names and overlong normalized fields. A message may contain line breaks as **inert plain text** but cannot become trusted HTML. Neither processing_ack nor request_id is a proof of consent/uniqueness. Never reflect submitted values in errors, logs or provider routing.
- Only configured public site origin(s) may use browser CORS, and reject inconsistent Origin where present; allow OPTIONS narrowly for preflight if required. **Origin, Referer, CORS, client IP and client-supplied challenge result are never authentication or CAPTCHA proofs**; non-browser direct requests remain explicitly in scope. Do not allow credentials, wildcard origins or browser-exposed secrets. CSP and script/processor disclosures change only after Indigo/Prism acceptance.
- Server config must contain nonempty allowed hostnames, expected Turnstile action, fixed sender and fixed BAGDigital recipient, stage-specific challenge secret, approved rate-store credentials, approved sender credential, plus enabled flag. **Default disabled; fail closed on missing, malformed, or test-only credentials in production.** Provider URLs and email destination are constants/configuration; never accept recipient, relay URL, From or HTML template from request.
- Source identity **MUST come from a verified ingress adapter**: known immediate trusted edge peer, configured/attested single canonical client-IP header overwritten at that edge, explicit proxy topology and no direct origin access. Do not trust caller X-Forwarded-For/CF-Connecting-IP without verified edge provenance; discard forwarded chains not established by Keel. On missing/ambiguous provenance **503 / no Siteverify / no send** rather than applying a weak guessed per-source quota. For Stage 1 use a mocked verified-ingress identity; no real host may be reachable until Keel proves this contract. Source quota keys use server-only HMAC with stage separation and expiring windows; do not log raw IPs. Secret rotation must coordinate a fail-closed drain or dual-version atomic migration, not silently reset existing live quotas or token claims.
- **Single atomic durable admission operation REQUIRED BEFORE Siteverify**, shared by all instances. In one serializable script/transaction check and reserve: (a) source budget in its time window, (b) global budget in its time window, (c) per-source and global in-flight verifier permits, (d) maximum distinct per-source rate-key cardinality, and (e) a single-flight replay claim keyed on HMAC(stage || Turnstile token) **ALONE**. Either all changes commit or none; no partial source-then-global increment, split cache, local Map or best-effort compensation. Quotas count admitted attempts even when challenge/email later fails; concurrency leases release by compare-and-swap on completion and expire conservatively after a bounded worker lease on crash. Rate/key/tombstone expiries derive from durable store time, not untrusted client or per-worker clocks. On limiter saturation return 429; on store disconnect/stale/non-atomic result/partial failure return 503, **no Siteverify or email**. Configure bounded cardinality/cost ceilings and redacted alerts. Keel must prove actual host/store can run the necessary transaction; example offline test budgets are not production sizing.
- Cloudflare Turnstile is a **candidate, not purchased/configured**. Before invoking Siteverify, the atomic admission operation must have durably claimed HMAC(token) **without request_id, payload fingerprint or client-origin variability**, stage/secret-scoped, with pending state and a claim TTL **at least 15 minutes** (strictly longer than the documented 300-second token lifetime plus bounded execution/clock skew). If the claim already exists, reject as in-flight/consumed, **do not call Siteverify a second time** even with different caller request_id or payload. State transitions via conditional compare-and-swap: ABSENT → PENDING → VERIFIED → CONSUMED, or PENDING → FAILED/CLOSED on error; **no reopening on timeout, crash, failed provider response, or pending lease expiry** before tombstone TTL. Keep the token digest tombstone until TTL; never store raw tokens. Claim secret-key rotation requires a coordinated stop/drain or atomic migration so mixed versions cannot bypass the lock. ONE Siteverify attempt only, short hard deadline, bounded provider response, server-only stage credential. Require provider success, exact stage hostname + action "marketing_inquiry", sane challenge_ts within the provider's **300-second** age window and configured skew tolerance; reject missing/unparseable timestamps, wrong host/action, expired/replayed response. The optional Cloudflare server-generated idempotency_key for *verification retries* is distinct from the application's replay claim; no Siteverify retries in Stage 1. Future retries need a separately reviewed safe protocol. Cloudflare test keys must fail closed in production; verifier outage/timeout/rejected response never proceeds to email.
- **Separate logical-delivery idempotency policy (bounded at-most-one send attempt per identical canonical inquiry, not exactly-once):** After confirmed Siteverify success, reserve an **independent** 24-hour stage-scoped logical key from server-HMAC of canonical normalized **name/email/business/service/message/processing_ack**; do **not** include request_id, CAPTCHA token or source IP. This makes a fresh challenge or changed caller request_id unable to re-send identical content in that window. The storage record contains only a keyed digest, status, timestamps, expiry and generic correlation ID, never raw inquiry fields. Atomically claim ABSENT → RESERVED → SENDING before invoking relay; later SENDING → ACCEPTED only on a definite provider-accepted result, or → FAILED/UNKNOWN on definite provider rejection or ambiguous timeout/crash. A crash/timeout after possible acceptance leaves a **terminal UNKNOWN** that is NOT retried or reclaimed while the 24-hour record exists, even with a new CAPTCHA. An in-flight duplicate returns a generic safe "pending/uncertain" response; terminal duplicates return a generic "may already have been sent—contact us directly" response, not an invented success. The UI preserves the draft and supplies copyable email fallback. No automatic retries, outbox or at-least-once promise. This may suppress two intentionally identical legitimate messages, while altered content after a new token can create another logical key: document both residuals and obtain privacy/retention acceptance for derived pseudonymous HMAC keys. Durable 24-hour TTL is a **proposed bound for review**, not approved long-term data retention. Fully transactional exactly-once inbox delivery remains out of scope.
- Email relay (provider still TBD) uses server-owned least-privilege credential and fixed allowlisted verified sender/recipient. Only accepted relay response from an unambiguous bounded call yields the accepted state; do not equate provider acceptance with actual inbox arrival. No caller-specified To/Cc/Bcc/From/provider URL; validated visitor mailbox is placed in a safe Reply-To only if relay supports injection-safe structured fields, otherwise text body only. Render body as inert plain text and explicitly sanitize CR/LF before any header-bound value. One outbound attempt maximum per claimed logical key; a timeout after possible delivery is UNKNOWN and **never silently resent**, even with a new challenge. Relay outage and unparseable reply are fail-closed and generic to visitor. No raw provider payloads, message content or secret in logs.
- Visitor response semantics: 200/202 **only** after definite relay API acceptance (text clarifies inbox arrival not guaranteed); 400/403 validation/challenge errors before sender; 409 generic duplicate/pending/unknown logical state without an information leak; 429 abuse quota; 502/503 relay/outage ambiguity or disabled service. On ambiguous timeout say **"We couldn't confirm delivery. Your inquiry might have been sent; please contact us directly if urgent."** Do not say "not sent" or prompt automatic duplicate submission. Preserve visitor draft and accessible retry/fallback notices; success or failure must not expose provider state, identity, digests or PII. No-store/nosniff/security headers and future script/CSP/challenge disclosure require independent Indigo/Prism review.
- Minimal telemetry: bounded timestamp, random request correlation ID, validation category, limiter outcome, Siteverify category, relay accepted/failure, latency bucket and on/off state. No raw request payload, recipient query string, names, email, full IP, captcha token, secret, stack trace or vendor payload. Rotate/expire pseudonymous abuse keys; decide metrics retention with Mara/Keel/Vesper. Kill switch can stop all submissions without losing website availability. A public form must never fall back to less protected FormSubmit when service is unavailable.

## Normative state machines and atomicity — ARCH24-01/02/03 correction

**Review precedence:** This section and the replacement public-contract bullets are normative; all earlier wording suggesting a composite CAPTCHA token/request_id/payload replay identity is superseded. The state machine is an architectural **test contract**, not verified runtime behavior. A future provider adapter MUST prove that its storage operations are atomic across multiple instances and retain stage isolation. If this cannot be demonstrated, the endpoint remains disabled.

### Atomic admission before third-party verification (ARCH24-01/02)

1. Reject disabled/missing stage config, missing required vendor secrets, invalid method/content type, unbounded/malformed UTF-8/duplicate-aware JSON, unknown fields, wrong processing_ack, invalid challenge syntax, disallowed browser-origin hint and absent trusted-ingress provenance **before** calling any quota, challenge or email dependency. Reject forged Origin; never treat it as authentication.
2. Derive trusted sourceKey = HMAC(rate-key-stage-secret, normalized verified ingress source), and tokenKey = HMAC(replay-key-stage-secret, raw Turnstile challenge token). **TokenKey excludes request_id, source IP and body fingerprint**. Keep only digests and stage-separated key versions; no raw token persistence.
3. Perform exactly ONE store-backed atomic admission transaction (e.g. verified serializable transaction or equivalent atomic script), which checks and updates **both** fixed-window source and global request budgets, source/global in-flight verifier permits, distinct sourceKey cardinality ceiling, and an ABSENT → PENDING tokenKey reservation. It must fail in one transaction with **no partial quota increment or replay claim**. If tokenKey already exists, reject without calling Siteverify. All store decisions use authoritative store time and stage namespaced keys. Stage 1 **illustrative mock budget only, NOT deployment approval**: source 5 attempts/15 minutes, global 120 attempts/15 minutes, source verifier concurrency 2, global concurrency 8, maximum 256 distinct source keys/window; actual thresholds and costs belong to Keel/founder.
4. Quota tokens are **consumed at admission**, independent of downstream provider success, so replayed and invalid challenges cannot trigger unmetered verification. If the store is disconnected, over capacity, cannot transact both budgets or cannot enforce cardinality, reject **before** provider invocation. The ingress/edge and shared rate-store must also have an independently proved upstream protection against malformed-request volumetric denial of service; pure Node parsing cannot replace platform WAF/cost limits.
5. Successful admission creates one durable tokenKey record {stage, keyVersion, status:PENDING, claimId, siteverifyIdempotencyKey:serverUUID, createdAt, expiresAt}, with expiry >= 15 minutes. Only the claim owner may call Siteverify and transition PENDING → VERIFIED/FAILED using conditional claimId/state compare-and-swap. **Pending crashes/timeouts become terminal non-retryable CLOSED/UNKNOWN until expiry**, not a lease that allows another verifier call. Conditional request must not "delete on failure" or refund an expiring replay tombstone.
6. Concurrency permits are bounded leases separate from the token replay tombstone. On completion release only the caller's exact lease using compare-and-swap; on worker crash, expire safely after maximum function runtime plus margin. The tombstone **must outlive the concurrency lease**, and expiry must not enable a second Siteverify while the 300-second vendor token remains usable. On stale lease without a terminal provider outcome, fail closed.
7. Siteverify is invoked **once**, after admission, with a hard 3-second mock deadline and an 8-KiB maximum verified response size (candidate test bounds, final Keel adapter caps pending). Reject timeout, non-2xx, unparseable/suspicious response, success=false, bad host/action and missing/invalid/stale challenge_ts. Do not accept a client-side challenge verdict. A provider verification idempotency UUID is persisted but **not used to permit an automatic retry**; Cloudflare documents an optional server-generated idempotency_key for a separately reviewable verification-retry strategy.
8. All instance races must see the same atomic store state. Mock *two parallel requests with the SAME CAPTCHA token but DIFFERENT request_id and message contents*, and hold the first Siteverify promise to prove exactly one verifier invocation and zero sends until the winner verifies and reserves delivery. Also test store failure, failed partial budget transaction, key cardinality saturation and a crash between each state transition.

**Key rotation:** Replay/rate/dedupe HMAC keys are independent of the Turnstile credential, and each record carries a stage-scoped keyVersion. Until the longest tombstone/24-hour dedupe retention expires, use a verified coordinated pause/drain **or** an independently reviewed atomic dual-key migration. A mixed fleet with different key versions must not accept requests (fail closed). Never silently reset quotas, token claims or delivery claims by changing HMAC keys.

### Separate durable logical-delivery reservation (ARCH24-03)

1. **First** secure admission and one verified challenge; **then** derive logicalKey = HMAC(delivery-stage-secret, canonical normalized form values) independent of CAPTCHA token/request_id/ingress IP. Exact canonical encoding is length-prefixed normalized fields in a fixed order, not ambiguous plain concatenation; include a canonicalization version in the key derivation. Only the keyed digest is retained in the proposed 24-hour record, not the message content.
2. In a separate single-key atomic operation, claim logicalKey ABSENT → RESERVED → SENDING, with durable state recorded **before** the one and only email relay invocation. If existing RESERVED or SENDING, refuse another send and show an in-progress/unconfirmed response. If existing ACCEPTED, FAILED or UNKNOWN, refuse another send within TTL and show an ambiguous-safe result; do not leak which state to a third party.
3. Definitive relay-accepted response conditionally moves SENDING → ACCEPTED; definite transport rejection moves SENDING → FAILED; timeout, connection loss after dispatch, crash or unknown HTTP response moves SENDING → UNKNOWN (or remains durable SENDING treated as UNKNOWN on recovery). **Never retry an UNKNOWN** and never let timeout release delivery idempotency state for immediate reuse. The attempt might have been accepted before the response was lost.
4. A retry with **the same challenge** is stopped by tokenKey before Siteverify. A retry with **a fresh challenge but the identical inquiry content** can verify again within quotas, but cannot claim logicalKey or cause another email. If an attacker or legitimate visitor modifies message content or identity, a different logicalKey can send after completing all gates; this remains an explicitly acknowledged *at-most-once per canonical content / retention window* guarantee, not person-level dedupe or exactly-once delivery.
5. The 24-hour dedupe TTL deliberately trades false suppression of intentionally repeated identical messages for avoiding duplicate accepted-but-timeout sends; no automatic resend even after definitive relay failure. After TTL a fresh valid challenge can submit again; do not claim unbounded exact-once semantics. On uncertain delivery, say it **may already have been sent** and offer a direct email/contact fallback that itself could generate a second copy. Any request to extend the retention or store inquiry content requires new founder/privacy/security approval.
6. No transactional outbox, worker retry, persistence of raw visitor messages or dynamic routing is authorized in Stage 1. A different reliability model requires a new reviewed design and owner decision. Relay must be a single fail-closed callable mock in Stage 1; a host/provider receipt and independent end-to-end evidence remain future release gates.

### Parser, ingress, egress and verification contract (ARCH24-04/05)

- **JSON:** Require a strict UTF-8 decoder in fatal mode (e.g. TextDecoder with fatal:true), a **duplicate-member-aware tokenizer/parser before object construction** that decodes JSON escape sequences in member names, rejects repeated decoded member names at every object depth, duplicate aliases, lone surrogates, excessive depth (top-level flat object only), NaN/Infinity, prototype keys and trailing data. Never claim stock JSON.parse alone can detect duplicate members. Pin/review the actual parser dependency and test malformed sequences in the subsequent Stage 1 PR.
- **Lengths:** Measure request cap and Siteverify response limit in UTF-8 **bytes**, field limits in Unicode **code points after NFC**; document exact whitespace trimming for each field, allow intentional message newlines as inert text, and enforce separate UTF-8 byte caps for all fields. Encoded JSON escapes count toward the **raw** 16-KiB envelope; decoding/normalization must not bypass a normalized field limit.
- **Trusted ingress:** Keel must document actual host's immediate trusted peer/edge, immutable canonical client-address header and defense against direct origin traffic. Neither arbitrary X-Forwarded-For nor client-supplied headers are adequate. Stage 1 mocks receive a sealed server-side attributedSource from the ingress adapter; unverified provenance returns 503, not a no-limit/global-quota fallback.
- **Provider response:** Harden Siteverify transport with fixed HTTPS URL, server-only secret, maximum 3-second timeout and 8-KiB decoded response cap as Stage 1 **mock target bounds**; enforce strict boolean success, bounded challenge timestamp age 0–300 seconds with defined small clock tolerance, exact action and environment-specific hostname allowlist. Distinguish challenge denial (403) from dependency unavailable (503) without logging provider contents. No Siteverify retry by default; a future optional idempotency_key retry protocol is a separate Vesper-reviewed change.
- **Secrets and adapters:** Production must fail closed if the stage, host binding, expected action, HMAC keys, rate store, challenge secret, delivery credentials, fixed sender/recipient, or disabled-by-default release flag is absent/misconfigured; Cloudflare testing keys are not valid production credentials. Stage 1 may only use injected fake secrets and mocked dependencies. Keel Infrastructure #29 MUST attest host/store atomic transactions, ingress IP provenance, provider relay authorization, Stage-specific secrets/egress allowlists and bounded hosting/WAF costs **before any reachable staging**. No actual vendor, Vercel project, store or mail service is selected here.
- **Operational lifecycle:** The proposed kill switch aborts before external calls and has independent monitoring. An unplanned runtime crash after provider email dispatch results in an UNKNOWN durable delivery record; emergency disable does not erase it. Old FormSubmit public HTML and previously issued provider token/endpoint are a **separate legacy decommissioning action** under Site #7 with owner permission and independent evidence; neither this document nor a merged new UI automatically retires it.

## Failure and abuse cases to independently review

| Attack/failure | Enforcement | Expected no-delivery result |
| --- | --- | --- |
| Direct forged POST, missing consent, false or arbitrary consent | strict backend schema, processing_ack == "yes" | 400; sender not invoked |
| Caller supplies recipient, action, _captcha=false or unexpected data | exact schema allowlist and fixed transport config | 400; sender not invoked |
| Missing/invalid/expired/replayed Turnstile token | mandatory Siteverify + host/action checks, token reservation | 403; sender not invoked |
| Siteverify reports different hostname/action or stale challenge | exact environment binding and timestamp | 403; sender not invoked |
| Siteverify timeout/5xx/malformed response | fail-closed dependency error | 503; sender not invoked |
| Overlong body, field, malformed JSON, duplicate keys or wrong MIME | strict max streaming size/parser/schema | 400/413/415; no Siteverify or sender |
| OPTIONS or GET abused | narrow CORS preflight; disallow unsupported methods | 204 for permitted preflight or 405 |
| Spoofed Origin or client IP | hints only; trusted edge attribution | never bypass quotas/verification |
| Per-source/global/cardinality/concurrency race, partial store commit or limiter unavailable | one atomic shared admission for both quotas, permits and token claim | 429/503; no verifier/sender |
| Concurrent same-token requests with different request IDs/payloads | durable HMAC(token)-only PENDING claim inside atomic admission before Siteverify | one verifier attempt, no second send |
| Relay accepted but response lost, crash or fresh-challenge replay | separate 24-hour canonical-content HMAC reservation with UNKNOWN state | no second send within bound; disclose possible delivery |
| Source site/host absent, disabled config or server kill switch | fail-closed startup/request guard | 503; no request to vendors |

Caller-supplied From/To or Reply-To CRLF, malicious HTML, request-id collision, double click with first relay promise held, relay accepted then response timeout, retry with SAME and NEW challenge, SENDING crash, definitive failure and expired TTL => fixed routing, only one email invocation per identical logicalKey/24h, correct durable UNKNOWN/ACCEPTED states, truthful ambiguous messaging, redacted telemetry, no blind retry.
